# 平台調研與分發裁決

v1.3｜查閱日期：2026-11-15。2026-11-17 更新倉庫與驗收裁決。自 v1.2 起只寫入 Yuki-Mobile，產品只裝在本人設備上，原始碼使用數字生命研究所的[公開 GitHub 倉庫](https://github.com/Institute-of-Agent-Life/Yuki-Mobile)。本文分別記錄固定提交、上游文件的聲稱、直接讀到的源碼與真機驗證。

**本輪範圍：** 以 `git fetch --depth 1` 取得 Mika、Poki 固定提交的唯讀副本，只讀文件與源碼，不執行其中任何腳本或 build。Yuki 與 Desktop 在本機的 HEAD 等於固定提交。**本輪沒有真機測試，也沒有重新讀取 Google／Apple 政策頁**；§7 沿用 v1.0 的閱讀結論，標為「暫定」，由發布卡重新核查。

## 1. 明確推薦

**Android 普通客戶端先做原生 Kotlin／Compose；iPhone 普通客戶端使用 SwiftUI。設備操作各自做獨立的實驗版，不作為普通客戶端上架的前置。**

普通客戶端放在獨立的 `Yuki-Mobile` 倉庫，是兩個原生專案。兩者共用 MOB-001 鎖定的後端合同、由後端程式產生的 golden vectors、設計 token 和 QA-001 驗收，不先共用全部 runtime。Mika 與 Poki 只用來研究平台能力和交接方式，不整包 fork。這是工程上的選擇，尚未做效能、耗電或總成本的比較測試。

v1.1 調整：手機操作分兩條路，各自沿用現有的方向。

- **系統能力（R-D1）**：依 #299 §5.7 與 C40～C44 的「系統 Intent 優先」，以設鬧鐘加讀回為第一能力。但現行 Yuki 沒有對應的 connector 資源，必須改後端，所以 **v1.2 暫緩**（DEV-004）。DEV-001 的手機端試作仍可先做，提前累積證據。
- **界面操作（R-D2、R-DI）**：沿用 Yuki 現有 protocol 4 的 `computer` 資源（截圖、元素樹、點擊，加上 journal 與 unknown 語義），由 DEV-008 在手機端做黑箱驗證，不新增 DTO，也不改 Yuki。

v1.0 的 `clipboard` 不採用：沒有合同，一般 App 的讀回也受系統限制。

## 2. 原生與共用方案的比較

| 候選 | 真正能共用的部分 | 額外維護與接手成本 | 本輪裁決 |
| --- | --- | --- | --- |
| Kotlin／Compose＋SwiftUI | schema、golden vectors、原 ID 語義、設計 token、後端 fixture | 要寫兩套 UI 與生命週期程式，但平台權限和工具鏈都看得見 | **採用**；兩端跑同一套故障驗收 |
| Flutter／React Native | 大部分 UI、部分資料與狀態程式 | Keychain／Keystore、背景、通知、Files、分享和操作器都還要原生橋接 | 目前不採用 |
| Kotlin Multiplatform 資料核心 | 部分 DTO、HTTP、outbox 邏輯 | Swift 互通、序列化與協程邊界都有成本 | 首版不加；等兩端重複邏輯穩定後再評估 |
| PWA／WebView 包殼 | 網頁對話與檔案列表 | 解決不了原生權限、背景可靠性與設備操作 | 只能作臨時唯讀入口 |
| Mika／Poki 整包改名 | 現成的本機 Agent UI 與能力 | 要拔掉模型帳號、Agent loop、記憶與排程；還有 GPL／AGPL／PolyForm 授權與品牌風險（§8） | 不採用 |

後端日後換成 Rust 核心，也不應迫使手機重寫：只要保持公開 wire schema、原請求查證、事件語義、版本語義，以及 MOB-001 的 golden vectors 和 QA-001 的驗收套件。

## 4. Yuki 與桌面接續依據

固定版後端已經具備：個人裝置與一次性碼、原入口 header、持久請求查證、Work inputs／cancel、事件 keyset 與 sync、原附件、不可變 artifact。這些足以支撐普通手機的第一切片。

**合同已有現成匯出與鎖定。** 合同由 `client_openapi()` 產生，`yuki client openapi` 會呼叫它。Desktop 的 `contracts/source.json` 與 `npm run check:contract` 鎖定同一份檔：Desktop 標示的來源是 `df133fbc`，在 `08164f67` 重新匯出逐字節相同。v1.0 認為要「再造匯出器」，這個判斷不成立。

**已有參考消費者：** Yuki 自帶的 `client_sdk.PersonalClient`／`Outbox` 和 Desktop `src/main/outbox/*`。兩者都是一個入口一個 outbox；GET `found:false` 時原號原內容續送；雜湊演算法與後端逐字元一致（`fingerprint.ts` 的跳脫範圍等同 Python 的 `ensure_ascii`，本輪以 U+007F／é／emoji 對照過）。

**已有隔離後端與故障點。** `tests.support.desktop_reference_server` 加上 `desktop_fault_fixture`，提供：commit 後丟 ACK（messages／uploads／inputs／cancel）、斷流、帶丟提示的刪除、原件到期、第二 Person 碼、超管切換、QQ 入口。缺少的只有「Work 成果帶檔」和「同一 Person 的第二個 App 入口」，由 QA-002 在 Yuki-Mobile 組自己的測試服務補上，不改 Yuki。

**現行 NativeConnector。** 它使用獨立的 connector 用途、`/agents/v1`、protocol 4。Main 的 `computer`／`browser` 工具帶 `device` 時，把單一命令送到本人設備，並以 `device_capabilities.computer.features` 把關；輸入先 journal 再執行，同一呼叫鍵重試回原回執，中斷記為 unknown（`local_device.py:86-135`）。這正好是手機**界面操作**需要的「觀察→動作→查證」骨架，所以 DEV-008 先用假手機 connector 對真實後端做黑箱驗證，確認有沒有缺口；有缺口就記為 blocked，不在手機端繞過。**系統能力**（例如鬧鐘）目前沒有資源或工具，需要改 Yuki，暫緩。

## 5. Mika：可借鑑的是平台操作與接手，不是本機大腦

### 5.1 README 所聲稱的事實

README 的平台表（第 140-142 行）列出三個要求：聊天、網頁、檔案需要 Android 11+；操作 App 需要 12+，推薦 14+（理由是背景畫面有自己的焦點）；Linux sandbox 需要 arm64。第 155 行說明，無線除錯會在換 Wi-Fi 或重開機時關閉。README 的「沒有 Mika server」指的是 Mika 自己在手機上管理模型帳號，不等於資料不離開手機。

### 5.2 本輪實讀的源碼位置

| 主題 | 固定提交中的路徑 | 讀到的事實 | 對 Yuki 的含義 |
| --- | --- | --- | --- |
| SDK 等級 | `app/build.gradle.kts:16-21` | `compileSdk 36`、`minSdk 29`、`targetSdk 35` | README 的 Android 11+ 是功能層級要求，不是 minSdk；Yuki 的 minSdk 仍由 MOB-002 依真機凍結 |
| 無障礙 | `AndroidManifest.xml:215-225`、`res/xml/accessibility_service.xml:5-6` | 宣告 `MikaAccessibilityService`，`canPerformGestures="true"`，`flagRetrieveInteractiveWindows` | v1.0 寫「未證實使用」不成立。Mika 的主屏操作路徑包含無障礙 |

### 5.3 對發布的影響

Android 14+ 上焦點隔離試作失敗，只阻擋 R-D2 在該機型上的背景 UI 操作，不阻擋 R-A。無線除錯或 helper 不可用時，不自動要求更多權限，也不改走另一條高權限的操作鏈。R-D1 的鬧鐘 Intent 只需要普通權限 `SET_ALARM`，不需要上述任何高權限。

## 6. Poki：五條路徑不能混成「iOS 已能遠控」

### 6.1 本輪實讀的來源

- **在機路徑**（`docs/ios-core.md:12-28`）：Poki App 經 loopback 隧道（`10.7.0.1`），連到手機自己的 developer services，再到 WebDriverAgent runner（XCTest，`127.0.0.1:8100`）。隧道由 PokiTunnel 提供（`native/ios-app/project.yml:12-33`，`packet-tunnel-provider` entitlement），或者使用外部 VPN。`project-external.yml` 是「不用 Network Extension」的簽名版本。
- **真機前提**（`docs/physical-iphone.md:11-50`）：Developer Mode、UI Automation、已掛載的 Developer Disk Image。DDI 版本與 Apple 個人化簽名可能拒絕（`STATUS=94`）。Wi-Fi 下 `devicectl` 可能找不到裝置。
- **簽名**（README 第 39、47、93 行）：免費帳號簽名效期 7 天，靠電腦端 Poki Setup 定期續簽。
- **驗證範圍**（`docs/verification.md:5-50`）：真機只在中文介面、直向驗證過。`sent:true` 只表示觸控已寫入連線，曾有 2／70 次丟觸控仍回 `sent:true`。CoreSimulator 與真機 bridge 都依賴 Apple 私有介面。

這些都是上游的說明與上游的測試，不是本輪的安裝或真機結果。

## 7. 官方平台政策與分發裁決〔暫定：沿用 v1.0 閱讀〕

### 7.1 Android

依 v1.0 的閱讀，Google Play 不允許用 Accessibility API 支撐自主發起、規劃與執行操作的應用，也不能把一般助理標成無障礙工具。Mika 的主屏路徑包含無障礙（§5.2），因此 **普通 Yuki 客戶端走一般分發；跨 App 操作版暫定為自用的獨立 APK，不宣稱已獲 Play 允許**。商店 build 不藏 dormant 操作功能等著遠端打開。MediaProjection 只負責畫面擷取，不提供輸入注入，每次 session 都要使用者同意。

### 7.2 iPhone

依 v1.0 的閱讀，App Review 要求使用公開 API。Poki 自述依賴私有介面，在機路徑又依賴 XCTest／WDA 和 Developer Mode，所以這條路徑不列為 Yuki 商店版的實作依賴。開發簽名能安裝，不等於能通過 App Store 審核。

### 7.3 分發矩陣（只裝在本人設備）

v1.2 不上架，所以 Play 和 App Store 的審核規則不構成門檻。但它們點出的風險（無障礙自主操作、私有 API、dormant 功能）仍然以「普通版與操作版分開打包」來控制。

| 產物 | 安裝方式 | 裁決 | 仍要的證據 |
| --- | --- | --- | --- |
| Android 普通版 | 本人金鑰簽名的 APK，可附在 GitHub Releases | 可開工 | R-A 候選通過；附件經 REPO-01 去識別 |
| Android 操作版 | 獨立 application ID 的 APK，只裝在本人測試機 | 可開工（R-D2） | 真機、停止與撤權、授權清冊 |
| iPhone 普通版 | 以 Xcode 安裝到本人裝置；不在 GitHub 發佈二進位檔 | 可開工 | R-I 候選通過、簽名帳號類型與到期日 |
| iPhone 界面能力 | 獨立 target，只裝在本人裝置 | 試作後再決定（R-DI） | DEV-003 的真機證據 |
| iPhone 私有 bridge | 本人裝置的研究環境 | 只做研究 | DEV-003 的源碼、授權與真機證據 |
| 推播 | — | 暫緩（需改 Yuki） | — |

| QA-002 測試服務未完成，或 Yuki 升版後組件不相容 | 阻擋各自依賴該服務的 A01、A06、A08～A10，以及 DEV-008 | Android 骨架與 HTTPS 入口驗證、iPhone 骨架實作、平台研究 |
| QA-001 的入口未在目標真機通過兩種網路的 `env-check` | 該平台的基本版測試環境尚未就緒 | 另一平台按自己的真機結果判定；可繼續本機功能開發 |
| DEV-008 發現後端缺口 | R-D2／R-DI 記為 blocked（需改 Yuki） | R-A、R-I |
| schema 缺首版欄位 | 阻擋相應的寫入功能 | 既有的安全讀取與 UI 骨架 |
| Mika 焦點隔離或無線除錯不穩 | 阻擋該環境的 R-D2 | R-A、R-I、R-P、R-D1 |
| 鬧鐘讀回無法確認（R-D1 暫緩期間的試作） | DEV-001 不能作為將來 DEV-004 的條件 | 保留 unknown；R-D2 的界面路線不受影響 |
| Poki 真機安裝、簽名或私有服務不可持續 | 阻擋該條 iPhone 操作路徑 | R-I、本 App 能力、App Intent |
| 上游 license 或品牌沒釐清 | 阻擋該程式碼或素材併入 | 自行實作 |

## 10. 查證缺口的最小完成清單

- **MOB-001：** 完成 Desktop 的 `Pairing.tsx`、`DeviceSecurity.tsx`、`media/content.ts` 逐函式 source-map；以後端程式產生 golden vectors。
- **DEV-002：** 補完 Mika 的 helper／adb 配對、虛擬顯示釋放、停止與清理呼叫鏈；在 Android 14+ 真機上驗 trusted 顯示的焦點。
- **DEV-003：** 先做本 App fixture 與 App Intent；Poki 五條路徑逐欄填寫。
- **DEV-008：** 以假手機 connector 對真實後端做黑箱驗證，確認 `screen_action` 是否預設桌面平台。
- **DEV-004（暫緩）：** 需改 Yuki 時，再依固定工具合同選出系統能力的最小接法。

本輪調研足以確定普通客戶端的合同方向、平台分工和不能混包的邊界；**還不足以承諾 Mika 或 Poki 的模組能直接移植，或任何手機操作版已可公開分發。**
