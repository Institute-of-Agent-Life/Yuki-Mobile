# 手機端提交級任務書

版本：v1.3｜2026-11-17（America/Los_Angeles）｜全部是**待實作、待驗收**的提交。

**範圍（自 v1.2 起）：只寫入 Yuki-Mobile。** Yuki 和 Yuki-Desktop 只作為固定版本、唯讀的依賴和消費者，不改程式、不改測試、不開分支。產品只裝在本人的設備上，原始碼放 GitHub。需要改 Yuki 本體的卡（系統鬧鐘能力、推播）移到文末的[暫緩卡](#暫緩卡需改-yuki-本體)。各版本的修正見[總任務書 §3](Yuki-手機端總任務書-v1.3.md#3-修正紀錄)。

## 執行規則

每張卡是 Yuki-Mobile 裡一個可審查的行為提交。確需多個 commit 時，保留父 ID 再加 `/1`、`/2`，子提交寫明還有哪些行為不完整；任一子提交未通過，父卡就不算完成。

Yuki 固定在 `08164f6732c14fca0396eb3411f8a82d6762aa8c`，Desktop 固定在 `a5687a66cf74485c94394e1008ddfbc0ebd926a2`，兩者都以唯讀 checkout 使用。開工時以 `git ls-remote` 記錄兩倉的遠端 main。main 已前進時，寫下新 SHA 並跑 MOB-001 的 `check`：通過就沿用；不通過，只重驗受影響的合同項。**不在 Yuki 或 Desktop 的工作樹裡寫任何檔案**：venv、pytest 暫存、後端資料根目錄都放在 Yuki-Mobile 的 `acceptance/out/`（已 gitignore）或系統暫存目錄。**注意：** 只把 venv 放到倉庫外還不夠。`uv sync` 會以 editable 方式安裝 Yuki，`hatch_build.py:20-24` 會把 SQLite 原生庫編進 `src/yuki/_native/`。這些檔被 `.gitignore` 遮住，`git status --porcelain` 看不出來（本輪就因此寫入過，已刪除，見總任務書 §2）。所以 `YUKI_BACKEND_TEST_ROOT` 一律用 `git archive` 匯出到倉庫外的副本，不直接用日常工作樹。

Yuki-Mobile 自願採用與 Yuki 相同的開發約束：E2E 優先，結束時產出可驗證、可重跑的產物；確需隔離測試時，**先寫全部失敗情境再寫程式**；不寫防禦性替代機制；不把未驗證的東西寫成已驗收。每張卡交付 commit SHA、實際命令、exit code、具名產物與未解問題。

**工具由負責卡建立，後續卡呼叫。** REPO-01 交付首筆提交與發佈規則，QA-001 建 `acceptance/run.py` 與故障代理，QA-002 建手機端自有的測試服務。MOB-002 建 Android Gradle 入口，MOB-009 建 Xcode project 與 scheme。只有標「本輪已執行」的命令有執行紀錄，其餘由各卡交付。

**如果發現非改 Yuki 不可：** 停在那裡。寫下源碼位置、最小改動與受影響的場景，把該卡狀態記為 `blocked`，不在 Yuki-Mobile 裡繞過後端的身份、授權或回執語義。

### `run.py` 合約

`python3 acceptance/run.py --case <Axx[,Ayy...]|smoke|desktop-handoff|all-core> --client <reference|android|ios|desktop> [--build <debug|release>] --server <reference|mobile-fixture> --output <dir>`

`python3 acceptance/run.py env-check --public-url <url> [--client <android|ios> --build release --networks wifi,cellular] --output <dir>`

- 省略 `--client` 時從開發機驗憑證、路徑前綴與 `/meta`。指定 `--client` 時，由已安裝的真機 App 分別在兩種網路發請求，記錄實際網路、build hash、信任設定和結果。開發機通過只用來確認入口可用。

- `all-core` 展開為 A01～A12。`--build` 預設 `release`；`debug` 只用於 M1 演示與開發，其結果不計入候選包。
- `desktop-handoff` 是 QA-003 的自驗 case（替身手機），不算任何 A 場景通過。
- 每個 case 寫一份 manifest，格式見[矩陣 §8](跨端介面與驗收矩陣.md#8-驗收產物格式與判定)。
- 要求的 case 只要有一個不是 `passed`，就以非零碼退出，並逐項列出 `failed`、`blocked`、`not_run`。
- `reference` client 是 Yuki 自帶的 `yuki client` CLI。它用來先證明後端與故障點，不代替手機或桌面的驗收。
- `--server reference` 使用 Yuki 原有的 `tests.support.desktop_reference_server`；`--server mobile-fixture` 使用 QA-002 的服務。

## REPO-01：首筆提交、授權、機密排除、證據去識別與 CI 骨架

**倉庫：** Yuki-Mobile，使用數字生命研究所的[公開倉庫](https://github.com/Institute-of-Agent-Life/Yuki-Mobile)。**直接前置：** 無。

**為什麼做：** 原始碼要上 GitHub，但驗收產物天然帶有 token、配對碼、裝置識別與私聊內容。第一個 commit 就要把邊界定好，後續各卡才不會把機密帶進歷史紀錄。

**擬新增路徑：** `LICENSE`、`README.md`、`.gitignore`、`.gitattributes`、`docs/publishing.md`、`tools/redact_evidence.py`、`tools/check_repo.py`、`.github/workflows/ci.yml`。

**本提交改動：**
1. **授權：** 預設 `AGPL-3.0-only`，與 Yuki、Desktop 一致。Yuki-Mobile 會收錄從 Yuki 匯出的 OpenAPI 與 golden vectors，也會引用 Yuki 的測試支援。選別的授權前，要先想清楚這些內容怎麼處理（見總任務書 §14）。不收錄 Mika 或 Poki 的任何程式碼、圖示、素材。
2. **`.gitignore`：** 排除 `local.properties`、`*.jks`、`*.keystore`、`*.p12`、`*.mobileprovision`、`*.p8`、`.env*`、`acceptance/out/`、`**/build/`、`DerivedData/`、測試 CA 的私鑰，以及配對交接檔。
3. **`tools/redact_evidence.py`：** 產物提交或附到 Release 之前，先去除 token、配對碼、伺服器網址、裝置序號、`device_id` 原值、私聊正文，以及未遮蔽的截圖；原始證據只留在本機。
4. **`tools/check_repo.py`：** 掃描已追蹤的檔案，看有沒有 `yuki_device_` 前綴、32 字元 base64url 碼、私鑰標頭、`Authorization:`。
5. **CI：** `check_repo`、MOB-001 `check`，以及（MOB-002 之後）Android `assembleDebug`。需要 Yuki 的 job 以 `actions/checkout` 取 `YuanYeYouTao/Yuki@<固定 SHA>` 到 runner 暫存目錄，只讀。CI 不放任何簽名金鑰；iOS 在本機用 Xcode 建置。

**關鍵失敗情境：** 驗收產物裡的 token 進了 git 歷史；release keystore 被提交；CI log 印出配對碼；把 Poki 圖示當成佔位圖放進倉庫。

**可重跑驗證：** `python3 tools/check_repo.py`；`python3 tools/redact_evidence.py --self-test`（用含假 token、假碼、假網址的樣本，驗證輸出裡都已去除）。

**具名產物：** `repo-check.json`、`docs/publishing.md`（Release 與證據提交規則）。

**完成門檻：** 一份含假機密的樣本，經 `check_repo` 必定失敗，經 `redact_evidence` 必定通過。

## MOB-001：鎖定 rev12 合同、golden vectors 與消費者 source-map

**倉庫：** Yuki-Mobile〔新〕；唯讀 Yuki、Desktop。**直接前置：** REPO-01。

**現有依據（本輪已核）：** Yuki `src/yuki/client_api/openapi.py:16-38`（`client_openapi()`／`export_openapi()`，含 `/client/v1` 與 `/agents/v1`），以及 `src/yuki/client_sdk/cli.py:33-35,69-71`（`yuki client openapi --output`）。Desktop `contracts/source.json`（Yuki `df133fbc…`、rev12、sha `14fd970b…`）與 `build-tools/check-contract.mjs`。在 `08164f67` 匯出的 OpenAPI 與 Desktop 鎖定檔**逐字節相同**（sha256 `14fd970b86a2ef393e1abec1aaae3aa56961304875af35454b000b2e8b98c101`）。

**擬新增路徑：** `contract-lock/source.json`（欄位照 Desktop 的 `contracts/source.json`）、`contract-lock/client-api.openapi.json`、`contract-lock/sse.md`、`contract-lock/golden/payload-hash.json`、`contract-lock/golden/text-normalize.json`、`contract-lock/coverage.md`、`contract-lock/source-map.md`、`tools/contract_lock.py`。

**為什麼做：** 手機要消費同一份公開合同。v1.0 打算在 Yuki 另建 `tools/mobile_contract/export.py`，但 Yuki 已有匯出入口，Desktop 也已鎖定同一份檔，所以不再造第二個產生器，也不寫入 Yuki。

**本提交改動：**

1. 用固定 Yuki 的現有入口匯出 OpenAPI，寫 `source.json`。`check` 同時核對 Yuki commit、`x-yuki-api-revision`、sha，以及 Desktop 鎖定檔的 sha。
2. OpenAPI 沒有涵蓋的部分，從源碼寫成 `sse.md`，每一條註明源碼行號：`/stream` 的 7 種 event（`sync`／`refresh`／`computer`／`character`／`conversation`／`work`／`activity`，見 `views.py:378-430`）、每連線從 1 起算的 `id:`、15 秒 keepalive、`ClientError` 時靜默結束、錯誤 status 對照（`http_errors.py:26-38`）。另外三個端點沒有 response_model：`DELETE /devices/{id}`（`http.py:631`）、artifact／attachment 二進位回應的 header（`http.py:468-504`）。
3. 由固定 Yuki 的 `yuki.client_api.identity.fingerprint`（`identity.py:61-64`）與 Python `str.strip` 直接產生 golden vectors，涵蓋 message／`client.work_input`／`client.work_cancel`／`client.upload` 四種操作，以及 é、emoji、U+007F、U+00A0、U+0085、U+001C～1F、U+FEFF。Kotlin 的 `trim()` 和 Swift 的 `.whitespacesAndNewlines` 與 Python 的空白集合不同，用錯會讓同號重送誤報 `request_conflict`。
4. `source-map.md` 把 Desktop 的配對、outbox、SSE、Work、上傳、下載逐項連到後端路由、回應模型與既有測試（起點見[矩陣 §3](跨端介面與驗收矩陣.md#3-http事件與檔案合同)「消費者」欄）。尚未讀的函式列為缺口，不填猜測路徑。
5. `coverage.md` 把 A01～A12 逐一對到 C01～C14 與 Yuki／Desktop 既有測試。**這是合同覆蓋，不是 A 場景完成條件**；A 場景只在手機卡和候選卡上判定。

**關鍵失敗情境：** 生成 DTO 把可空欄位變必填，或拒收 `PublicProjection` 允許的額外欄位；把 SSE `id:` 當持久游標；未知 event（如 `refresh`）讓解析器停止；normalization 用平台預設 trim；Desktop 鎖定檔與 Yuki 匯出不一致卻照常通過。

**可重跑驗證：** `python3 tools/contract_lock.py export --yuki-python "$YUKI_BACKEND_TEST_PYTHON"`、`python3 tools/contract_lock.py check --desktop-root "$YUKI_DESKTOP_ROOT"`，以及 `python3 tools/contract_lock.py golden --yuki-python "$YUKI_BACKEND_TEST_PYTHON" --check`。

**具名產物：** `contract-lock/` 全部檔案、`contract-check.json`（三方 sha、commit、revision）。

**完成門檻：** 首版用到的每個欄位、錯誤碼與 SSE event 都有源碼位置；golden vectors 由後端程式產生，不是手寫；後端 main 前進後重跑 check，可以看出哪些項目受影響。

## QA-001：以 Yuki 既有隔離後端建跨端 runner 與故障代理

**倉庫：** Yuki-Mobile〔新〕；唯讀消費 Yuki 測試支援。**直接前置：** REPO-01。

**現有依據（本輪已核）：** `python -m tests.support.desktop_reference_server --root DIR --state-file FILE --port 0` 會裝配原 ApplicationContainer、SQLite、App／Work／Social、個人與 connector 路由，以及腳本化模型（`client-api.md:372`；`desktop_reference_server.py:272-301`）。state 檔給出 `base_url`（含 `/role/test` 前綴）、owner／nonowner 配對碼與 artifact 狀態。已有的 `__test/*` 故障點見 `desktop_fault_fixture.py:171-334` 與 `soul_reference_server.py:383-447`，對應的 6 個單元測試本輪已通過。

**擬新增路徑：** `acceptance/run.py`、`acceptance/backend.py`、`acceptance/fault_proxy.py`、`acceptance/manifest.schema.json`、`acceptance/cases/smoke.py`。

**為什麼做：** 跨端驗收要用真的身份、資料庫、Work、Social 和檔案；只有模型可以換成腳本。v1.0 的 QA-001 同時寫 Yuki 和 Mobile 兩倉；實查後，後端隔離服務和大部分故障點都已存在，缺的部分由 QA-002 在手機端補上。

**本提交改動：**

1. `backend.py` 用上表變數啟動固定 SHA 的參考後端，讀 state 檔，結束時清理暫存根目錄。
2. `fault_proxy.py` 是 HTTP 反向代理，可按方法加路徑規則注入故障。`drop-before-forward` 表示請求沒有到達後端。`drop-after-upstream` 表示已讀完後端完整回應（後端在 commit 後才回應），再關閉連線或回 `503 {"problem":{"code":"unknown"}}`。另有延遲、截斷 SSE、斷流。代理只監聽本機。
3. **真機 HTTPS 測試入口。** 在代理前面接有固定主機名、憑證可由系統信任鏈驗證的 HTTPS 入口，Wi-Fi 與行動網路都使用同一個 `YUKI_DEVICE_TEST_URL`（見[總任務書 §7](Yuki-手機端總任務書-v1.3.md#7-配對與安全)）。手機側入口只轉發驗收使用的產品 API。`__test/*` 和原始狀態檔由本機 runner 直接存取。`env-check` 先從開發機查 `/meta`，再由各平台卡用真機記錄兩種網路的結果。
4. `run.py` 實作上面的合約。smoke 以 `reference` client 跑：配對 owner 碼，然後在 `drop-after-upstream` 下送 message。接著 `yuki client request <U>` 必須得到 `found:true`，原號重送得 `replay:true`。換成 `drop-before-forward` 後，查詢必須得 `found:false`，原號重送才首次接納。

**關鍵失敗情境：** 代理在轉發前就截斷，卻記成「已提交後丟回應」；代理改寫 `Authorization` 或跨 origin 轉送；測試入口只在區網可達，切到行動網路就連不上；入口把後端或代理暴露給不相干的網路；state 檔的 base path 被丟掉；後端沒啟動成功，case 卻判 `passed`。

**可重跑驗證：** `python3 acceptance/run.py --case smoke --client reference --server reference --output acceptance/out/smoke`。用 `python3 acceptance/run.py env-check --public-url "$YUKI_DEVICE_TEST_URL" --output acceptance/out/host-endpoint` 檢查 HTTPS 入口。任何未實作的 case 以非零碼退出。

**具名產物：** `harness-smoke.json`（兩種故障點的請求、回執與 `found` 對照）、`run-manifest.json`、`device-endpoint.json`（host probe 或裝置 probe、憑證核對和請求結果）、資料隔離與清理說明。

**完成門檻：** 接納前／接納後兩種斷線可以用真實回執區分。host probe 讀得到正確前綴下的 `/meta`，手機側入口拒絕 `__test/*`。兩端實機結果分別由 MOB-002、MOB-009 交付。

## MOB-003：Android 同入口配對與獨立裝置撤銷

**倉庫：** Yuki-Mobile〔新〕。**直接前置：** MOB-001、MOB-002、QA-001、QA-002。

**關鍵失敗情境：** 裝置已撤銷，推播仍向舊 token 送出正文；通知帶來的 Work ID 繞過 ACL。

**可重跑驗證：** `uv run pytest tests/integration/test_client_push.py -q`，供應商用 fake adapter，涵蓋過期 token、重複通知、錯 Person 與撤銷。

**具名產物：** `push-contract.json`、`push-backend.json`、資料流與供應商清單。

**完成門檻：** 只增加提示，不改變 Work 完成與回執；新能力有正確的版本號。

### PUSH-02：Android 通知回原 API

**倉庫：** Yuki-Mobile〔新〕。**直接前置：** PUSH-01、MOB-006。

**擬新增路徑：** `android/.../push/`、通知權限 UI。

**本提交改動：** 有 GMS 的裝置以 FCM 作候選，先只做一種通道。點擊通知只負責導航，然後重新讀原 API。拒絕通知、沒有 Google 服務的情況都要能照常接續。

**關鍵失敗情境：** 通知比資料投影先到；工作已刪，仍打開舊快取；通知權限被拒，App 因此卡住。

**可重跑驗證：** `run.py --case A13,A04 --client android`；真機測背景、冷啟、拒權與無通知補讀；記錄實測延遲，不下普遍結論。

**具名產物：** `android-push.json`。

**完成門檻：** R-P Android 候選包通過，資料完整性不依賴推播。
