# 跨端介面與驗收矩陣

v1.3｜2026-11-17。本文以固定後端 Yuki `08164f67` 的源碼與文件為準，列出已核對的合同和手機端應實作的驗收。自 v1.2 起只寫入 Yuki-Mobile：後端與桌面都使用固定版本，不做改動。驗收用的後端是 QA-002 在手機端組出的測試服務，它引用 Yuki 的真實組件。

執行證據來自 2026-11-15 的 Yuki 既有測試與 OpenAPI 匯出（見 §5.0）。截至這次修訂，手機端 A01～A20 都是 `not_run`。模型替身、裝置替身、模擬器和真機的結果各自記錄。

## 1. 不可混淆的五種事實

| 事實 | 讀取依據 | 不可拿什麼代替 |
| --- | --- | --- |
| 請求已被接納 | `GET /requests/{id}` 回 `found:true`，且 `operation_kind`／`target`／`payload_hash` 與本機一致 | HTTP 連線曾建立、輸入框已清空、收到 503 |
| 請求未被接納 | 同一入口查詢回 `found:false` | 傳輸逾時、`unknown`、`unavailable` |
| 原輪次結束 | 原 request 的 `turn.state=ended` | 長時間沒有訊息、模型輸出 final 字樣 |
| Work 完成或取消 | Work 的 state、revision，以及 cancel 回執（失敗也有回執）與實際收攏 | App 關閉、按過停止、輸入已入隊 |
| 結果已交付、檔案版本 | 原 Social 出站事件、`artifact_id` 與 version（SHA-256） | 沙箱裡有檔案、Work 說完成、目前的同名檔 |

這些區分沿用後端 Client API 文件（`docs/architecture/client-api.md`，下稱 [Y1]），手機不另建完成計數器。

## 2. 身份、入口與識別碼

文件符號：`P` 是目前 Person；`B-A`／`B-B` 是兩個原 App Binding；`C-A`／`C-B` 是原 Conversation；`D-D`／`D-A`／`D-I` 是桌面、Android、iPhone 裝置；`W` 是原 Work；`U` 是原請求 UUID4。HTTP 測試必須換成真實合法的 ID。

**預設入口怎麼決定（v1.1 實查）：** 裝置記錄只保存 `person_id`，也就是碼所屬的 Person，不保存 binding（`src/yuki/identity/credentials.py:102-134`）。沒帶 `X-Yuki-Entry` 時，預設入口是該 Person 的 App binding（`src/yuki/client_api/identity.py:178-192`）。
- 裝置用 `POST /link-codes` 簽發的碼，Person 是當下所選入口的 `request_person_id`。所以在 B-A 下簽發，新裝置預設就是 B-A。
- operator 用 `--person <root>` 簽發時，若 root 自己沒有 App binding，`/pair` 會為它**新建**一個入口（`identity.py:407-427`）。

首條閉環要求三端使用同一實例、同一目前 Person、**同一原 Binding**。Person 相同但 Binding 不同，屬於另一個跨入口情境（A06）。

outbox 以「實例 origin＋`request_person_id`＋`binding_id`＋`conversation_id`」為 owner，一個入口一個 outbox。Desktop（`src/main/outbox/index.ts:19-41`）和 Python 參考 client（[Y1] 第 259 行）都是這個做法。`X-Yuki-Entry` 同時作用於發送、Work inputs、上傳、請求查證與快照。`X-Yuki-Conversation` 只用於 ACP 多會話，App 手機不送。

人物歸並保留原入口與 namespace。帳號轉移不會把歷史、Work 或 connector 所有權轉給新的持有人。所選入口無法證明時就停止派發。

### 已核對的 wire 例子

```json
{"request_id":"00000000-0000-4000-8000-000000000001","text":"加上運費","attachments":[]}
```

這是普通 `/messages`，**不是** Work 補充。原 Work 的補充送到 `/works/W/inputs`，body 是 `{request_id,text}`。同一個 UUID 不能先用在 message 又改用在 input：兩者在同一入口共用 namespace，後端會回 `request_conflict`。

```json
{"request_id":"00000000-0000-4000-8000-000000000002","expected_revision":7}
```

這是對一個明確選定的 Work 發的 cancel。`expected_revision` 是使用者看過並確認的那個 Work revision，不是 API revision。

## 4. 收斂、未知與重試判斷

| 觀測 | 手機顯示／動作 | 自動重試界線 |
| --- | --- | --- |
| 本機保存失敗 | 草稿未送出 | 不發 HTTP |
| 傳輸中斷、收到 `unknown`、5xx | submitted／待確認 | 先以原入口 GET 原 UUID |
| `found:true`，內容一致 | accepted；顯示已確認的輸出 | 只查詢與補讀，不再派發 |
| `found:true`，內容不一致 | 衝突，保留原項 | 停止；不覆寫原 hash，也不換號 |
| `found:false`，本機是 submitted | 仍是待送 | **原號、原內容續送**。這是後端明示的冪等路徑（[Y1] 第 167-171、193-200、235-236 行），Desktop 和 Python 參考 client 都這樣做 |
| 查詢本身失敗 | 保留 submitted | 稍後再查；不換號 |
| `unavailable` | 暫時無法處理 | 後端確認是未提交的 busy，才回這個；仍走「先查後送」 |
| `request_conflict` | 原號已被不同內容、目標或操作使用 | 終態；原號不再用 |
| `precondition_failed` | 展示原 Work 的狀態與 revision | 原號已記成失敗；新的取消意圖用新 UUID，並讓使用者再確認 |
| `unauthenticated` | 停止派發，引導重新配對 | 不無限重連，不換用別台裝置的 token |
| `forbidden`／`owner_required` | 隱去受限功能，清除受限快取 | 不換入口繞過權限 |
| `not_found` | 原資源不可讀，或原件已缺失 | 不據此推出永久不存在 |
| 新版 DTO 不相容 | 停止受影響的寫入，保留草稿 | 不因 revision 較大就強行解析 |

**沒有可查回執的寫入：** `/pair` 的回應丟失時只能重發碼，並撤銷孤兒裝置。新的 `link-code` 以原 `request_id` 重放時，只回 `code_id`，不回明文（Desktop `device-security.spec.ts` 已涵蓋），要看到新碼就得重新簽發。

### 本機 outbox 的必要資料〔設計要求，不是新增 wire DTO〕

每筆紀錄包含：owner（實例 origin、`request_person_id`、`binding_id`、`conversation_id`）、原 UUID、endpoint、target、正規化 payload、payload_hash、狀態、已確認回執的引用、錯誤，以及本機時間。附件另記原件摘要與可用性。token 只保留安全儲存的引用。

**payload_hash 的算法：** `SHA-256(json.dumps([operation, target, payload], sort_keys=True, separators=(",",":")))`，ASCII 跳脫使用預設（`identity.py:61-64`）。payload 都不含 `request_id`，四種操作如下：

| operation | target | payload |
| --- | --- | --- |
| `message` | 原 `conversation_id` | `text`＋`attachments`＋可選 `agent_target` |
| `client.work_input` | `work_id` | `text`＋可選 `agent_target` |
| `client.work_cancel` | `work_id` | `expected_revision` |
| `client.upload` | `request_person_id` | `filename`／`kind`／`sha256`／`size` |

正文在後端以 Python `str.strip()` 正規化。Kotlin／Swift 必須通過 MOB-001 由後端程式產生的 golden vectors，不得用平台預設的 trim 或 JSON encoder。

### A01 桌面關閉，手機接回同一項 Work 並取回原檔

**起點：** 桌面 D-D 使用 QA-001 的 HTTPS 測試網址，以 owner 碼配對到 P 的 B-A。runner 先 arm `__test/work-scenario-artifact`，再由桌面發訊息。伺服器建立 W 並進入 `waiting_user`。runner 核對 Work 的 `trigger_event_id` 與桌面訊息回執是同一事件，且回執的 `principal_id` 對應 D-D。在桌面以 B-A 簽發 chat 碼，透過 QA-002 核對簽發入口後結束桌面 App。

**操作：** 手機兌換交接碼，核對 `/me.binding_id` 等於 B-A，sync、讀取 W、補一句運費要求。W 完成後，runner 用 `workspace-change` 把工作目錄裡的同名檔改成 H2。手機從 W 的 `results[].artifacts` 下載 F@H，再重開桌面另存同一結果的成果，計算兩份檔案的雜湊。

**觀察：** 手機提交一個原 U，得到原 `event_id`／`input_id`；W 不換 ID，預算不重置。手機與桌面看到同一個結果事件，各自下載的 F@H SHA-256 相同，並且不是 H2。關閉桌面不會停止後端。

**通過：** 同一 W、同一補充、同一結果事件、同一檔案版本。負例：以 nonowner 讀 W 和 F，必須被拒。只有真手機跑的結果算數；QA-003 用 `reference` 替身手機的自驗不算 A01 通過。Android 版先以 debug 包單獨跑一次，作為里程碑 M1；候選包再以 release 包重跑。iPhone 版要完整重跑，不能拿 Android 結果代替。

責任：MOB-008／MOB-013／QA-003／QA-002；產物：`desktop-android-e2e.json`／`desktop-iphone-e2e.json`、`desktop-handoff.json`；環境：真實桌面 App（不改程式）、真實手機與隔離後端。

### A02 配對成功、回應遺失，與精確撤銷

**起點：** 桌面在 B-A 下發一次性碼，手機用 C01 兌換。QA-001 的代理以 `drop-after-upstream` 截斷 `/pair` 的回應，此時後端已建立裝置。

**操作：** 手機顯示「可能已建立裝置，憑據未保存」，同時顯示本機標籤短碼，不自動重用原碼。桌面從 `/me.devices` 依標籤短碼與 `created_at` 找到孤兒裝置，帶 `request_id` 撤銷後再發新碼。另外測重複碼、過期碼、格式錯碼，以及撤銷回應遺失後用 `/requests/{id}` 查回原回執。

**通過：** 其他裝置仍有效；log 中沒有碼和 token；新手機確實進入 B-A。若無法唯一定位孤兒裝置，不自動刪除其他同名裝置。

責任：MOB-003／MOB-009；產物：`pairing.json`／`ios-pairing.json`。

### A03 Wi-Fi 轉行動網路，最後一條提示丟失

**起點：** 手機已載入到事件 E，W 正在執行，SSE 經 Wi-Fi 連到 QA-001 的 HTTPS 測試入口。候選包驗收前，使用同一個 release build 完成兩種網路的 `env-check`。

**操作：** 切換到行動網路，同時用 `__test/disconnect` 或代理截斷串流；後端在斷線期間完成 W。重新建立串流後，先處理 sync，再按持久游標補頁。

**通過：** 切到行動網路後，以同一網址和 release 信任設定連回同一後端，讀到最後的結果。每個 event ID 只出現一次。記錄操作前後的實際網路及 build hash，另測「先快照後訂閱」與「先訂閱後快照」兩種競態。

責任：MOB-004／MOB-010；產物：`sync.json`。

### A04 鎖屏、切背景、程序終止後回到工作

**起點：** 手機停在 W 詳情頁，然後鎖屏或切到背景；另跑一個程序被終止的變體。

**操作：** 手機停止串流期間，後端產生新事件。回到前景後重新核身份、sync，並核 W 的 revision。推播完全不啟用。

**通過：** 回前景後補齊同一批事件；連不上時顯示最後同步時間與離線狀態，不把快取標成最新。不用常駐音訊、定位或不必要的前台服務保活。

責任：MOB-004／MOB-010；產物：`foreground-reconcile.json`。

### A05 補充已接納，HTTP 回應丟失

**起點：** 手機對 W 存好 U 與正文後送 `/inputs`。代理在後端 commit 之後丟棄回應（真機用 `drop-after-upstream`；進程內則用 `__test/lose-next-work-response/inputs`），隨後終止手機程序。

**操作：** 重開後先用原 `X-Yuki-Entry` 查 `/requests/U`，比對操作、W 與 payload_hash。另跑接納前斷線及原號續送、用同入口的另一個測試憑據透過 API 查證並重放原 U，以及同 U 換正文的負例。桌面 UI 核對結果只出現一次。

**通過：** 原 event、mailbox input 與 request 一一對應且只有一筆；回傳原 `event_id`／`input_id`；不同 payload 被拒絕。不能換一個新的 U 再送來掩蓋未知。

責任：MOB-005／MOB-010／QA-003；產物：`request-recovery.json`。

### A06 同一 Person 不同入口，不能偷換原請求

**起點：** P 同時有 B-A／C-A，以及 QA-002 的 `__test/second-app-entry` 建立的已歸並 B-B／C-B。手機在 B-A 的 outbox 留有一筆 submitted U，畫面切到 B-B。

**操作：** 恢復 U 時必須在 B-A 下查詢。使用者另外在 B-B 明確對 W 送新的 inputs V，由後端按目前本人與原 Work 的 guard 判斷。B-B 的普通消息不能當成 W 的補充。

**通過：** U 的 namespace 不變；V 有自己合法的來源，但 W 的原預算與投遞位置不變。入口停用、人物歸並、原身份禁用各跑一個負例。

責任：MOB-005／006／010／011；產物：`entry-isolation.json`。

### A07 取消時 Work 已變更，另一個 Work 正在運行

**起點：** 手機開著 W1@r，桌面補充了一句，使 W1 的 revision 改變；同時活動清單出現 W2。

**操作：** 手機以原 U 和 `expected_revision=r` 取消 W1。衝突後只刷新 W1。之後以新的 U′ 和新的 revision 再次確認取消。另測一次取消成功、但回應遺失（`__test/lose-next-work-response/cancel`）。

**通過：** 衝突不會自動換 revision 重派；以 U 重放只得到原來的 `precondition_failed`；取消只作用在 W1。「取消已接納」與「實際已收攏」分開顯示。

責任：MOB-006／MOB-011；產物：`work-conflicts.json`。

### A08 本人 QQ 群 Work 的有限投影

**起點：** runner 呼叫 QA-002 的 `__test/qq-group-work`。此 fixture 先掛群 Work 劇本，再用 P 的 QQ 身份在測試群裡 @Bot，經 Yuki 的 processor 建立 W-Q 並進入 `waiting_user`。QA-002 記下原群會話 ID。

**操作：** 手機顯示原群來源與結果投遞位置。W-Q 等待補充時，先以 nonowner 裝置呼叫 `/works/W-Q/inputs`，再由本人在手機上補充。W-Q 完成後，從 `__test/facts` 核對記錄型 sender 的投遞。手機只呈現個人的 Work 投影。

**通過：** nonowner 被拒且 W-Q 沒有新增 input。本人補充成功並取得原 `event_id`／`input_id`。`result_delivery.conversation_id` 和 sender 記錄的目標仍是原群，手機補充只進 W-Q。R-A、R-I 以這組 fixture 驗收。實際 QQ 群投遞在本人授權的測試群另跑並留下獨立紀錄。

責任：MOB-006／MOB-011；產物：`qq-work-acl.json`。

### A09 撤銷手機、人物禁用與降權

**起點：** 手機正在讀 W、已建立串流。三個變體各自從有效憑據開始，分別測桌面撤銷手機、以 QA-002 的 `__test/source-enabled` 停用來源 Person，以及以 `__test/superuser` 把 P 降為非超管。

**通過：**
- **撤銷手機：** 不會取消伺服器上的 W，也不會撤到其他裝置。串流結束後，手機以 GET `/me` 得到 `401`，隨即停止送出、清掉本機憑據並遮蔽快取。
- **禁用來源身份：** 停用來源 Person 後，該來源的憑據讀 `/me` 得 `401` 並停止送出。同一歸並人物下另一個啟用來源仍可讀 `/me`（`test_disabled_source_and_revoked_device_are_not_revived_by_merge`）。
- **降權：** 沿用同一憑據，`GET /me` 回 `200` 且 `is_superuser:false`。手機更新身份，隱去當前版本的受限功能並清掉相應快取，一般聊天和 W 照常可用。EXT-02 再以同一變體驗受限 API 的 `403` 與 SOUL 快取清理。

責任：MOB-003／009、EXT-02；產物：`revocation.json`。

### A10 原附件、原成果版本與 bytes

**起點：** 上傳附件 M，訊息引用 M；W 產生 F@H（QA-002）。之後 `workspace-change` 把工作目錄裡的同名檔改成 H2。

**操作：** 桌面與手機都從原結果事件下載 F@H。另測：附件 M 被清理（`__test/expire-attachments`）、版本錯誤、另一個 Person、token 被撤銷、傳輸被截斷、bytes 雜湊不符。

**通過：** 兩端 F@H 的 SHA-256 相同，沒有偷偷拿 H2。upload 回執還在但附件 bytes 已缺失時，如實顯示原件不可讀。

責任：MOB-007／012／QA-003；產物：`artifact-check.json`。

### A11 安裝、TLS、路徑前綴與合同不相容

**起點：** 剛安裝的手機分別連到：合法的測試後端、帶 `/role/test` 前綴的後端、錯誤 URL、不受信憑證、缺少必要能力的服務。

MOB-002／009 先驗安裝、`/meta` 與 TLS。MOB-008/2、MOB-013 用實際簽名的候選包驗完整 A11，包括配對後的重導向和已有草稿時的合同不相容。

**通過：** release 只靠系統預設信任鏈，不忽略憑證錯誤，也不因為測試而信任自訂 CA；跨 origin 重導向時不帶 token；保留路徑前綴；不相容時停止寫入，但不丟草稿；新 API revision 不自動視為已驗證。

責任：MOB-002／008／009／013；產物：`compatibility-install.json`。

### A12 歷史被修訂或刪除，舊快取不復活

**起點：** 手機載入一頁歷史與 W 卡片後離線。後端以 `__test/events/{id}?lose_hint=true` 刪除一筆可見來源。

**通過：** 回到前景後，generation／revision 改變，手機從頭重讀。舊正文、附件按鈕與受影響的 Work 投影不從本地快取復活；提示佇列溢出導致串流結束時，也能收斂。

責任：MOB-004／010；產物：`history-revision.json`。

## 6. 獨立擴充情境 A13～A20

### A13 推播只定位，不構成授權

通知只帶最少的定位資訊。測前景、背景、冷啟、重複、亂序、丟失、拒絕權限，以及 provider token 過期。點開通知時重讀 `/me` 和原 API。手機撤銷後停止送提示。假供應商驗後端，實際 FCM／APNs 在真機上驗送達，兩者分列。

責任：PUSH-01～03（暫緩：需改 Yuki）；發布：R-P（暫緩）。

### A14 一個本人授權的手機系統能力，可讀回效果（#299 C40、C42、C44）

能力是「設定明早七點的鬧鐘」：用 `AlarmClock.ACTION_SET_ALARM` 交給系統，再用 `AlarmManager.getNextAlarmClock()` 讀回。

- **DEV-001：** 只在本機驗四態，即已交給系統、等待用戶處理、已確認、未知。
- **DEV-005：** 改用獨立的 connector 憑據，經 DEV-004 的接法連到同一個隔離後端；在 App 入口和 QQ 入口各說一次。

成功要同時有讀回值和原操作回執。以下情況都不能執行：chat token、他人的裝置、已撤銷的 connector、本機能力開關未開、群裡的其他人。只撤銷 chat 裝置不影響 connector；反過來也一樣。本人有兩台手機都授權時，以 Work 等待詢問一次。

責任：DEV-001／004／005（暫緩：DEV-004 需改 Yuki）；產物：`android-system-action.json`、`device-operation-receipts.json`；發布：R-D1（暫緩）。fake-device 只驗協定，不驗 OS 效果。

### A15 動作已做但回應遺失，不能再設一次（#299 C41）

原操作 O 設好 07:00 的鬧鐘之後，截斷回應，再重連；以原 O 查 journal 與後端原操作，用 `getNextAlarmClock()` 讀回。另外在「Intent 送出之後、journal 標記之前」殺掉程序，刻意製造 crash gap。派發之後手機斷網，原 Work 不取消。

能證實時，回傳原效果；不能證實時維持 unknown，並阻止自動重設。**這個場景不准出現第二個鬧鐘，也不准換新 ID 重做。**

責任：DEV-004／005（暫緩）；產物：`unknown-effect.json`。界面操作的同類要求，併在 A16 的 fixture variant 中驗。

### A16 界面觀察失效、停止與人工接手（#299 C43）

分兩個 variant。**fixture variant**（DEV-008 以假 connector 驗後端，DEV-009 在真機的本 App 計數器上驗）：讀計數 → 點一次 → 讀回。截斷回執後重連，在「點擊之後、journal 標記之前」殺掉程序；能證實就回原效果，不能證實就維持 unknown，不准讓計數變成 2。**cross-app variant**（DEV-006）：在指定的 fixture App 或受驗的 trusted 虛擬顯示上，走同樣的 `computer` 動作。先觀察；再故意切畫面、旋轉、換焦點，讓舊座標失效。使用者按停止並接手；恢復自動之前必須重新讀畫面。

鎖屏、權限關閉、helper 掉線、WSS 斷線各跑一次。只用 trusted 虛擬顯示；退回 untrusted 的機型，列為拒絕啟用。必須讀計數值作為效果，不能只看畫面有變動。

責任：DEV-002／008／009／006；發布：R-D2。

### A17 iPhone 各路徑分開實測

用同一個不破壞資料的 fixture 任務分欄記錄：本 App fixture、公開 App Intent／捷徑、Mac MCP＋Simulator、Mac 中繼＋真機、在機 Poki 參考路徑（PokiTunnel 或外部 VPN → WDA）。沒有設備或簽名的欄位標 blocked。

責任：DEV-003／008／007；發布：R-DI。

### A18 記憶、安排與角色的資源別授權

用四種身份變化驗證：本人、他人、SELF、超管降權。

責任：EXT-01／02。

### A19 手機觀看角色電腦並接手

在真實 Manager 環境中，測 ticket 過期、第二人競爭、鎖屏、降權、網路中斷、歸還回應遺失。沒有 Manager 環境時標 blocked。

責任：EXT-03。

### A20 語音、分享與相機仍走同一媒體鏈

從系統分享冷啟 App，先確認入口和附件再發送。辨識出來的文字不直接當成執行指令。

責任：EXT-04。

## 8. 驗收產物格式與判定

每份 manifest 至少記錄 case ID、started_at、client platform、機型、OS build、後端／桌面／手機的 commit、build 類型與 hash、入口與原 ID 的去識別對照、fault point、steps、expected、observed、evidence paths、status、限制，以及重跑命令。A03 與 HTTPS `env-check` 另記實際網路及 HTTPS 主機、路徑前綴、信任結果的對照。網址原值留在本機證據。

status 只能是 `passed`／`failed`／`blocked`／`not_run`。`blocked` 指缺設備、權限、依賴或環境；`failed` 指實際跑了但觀察不符，兩者不能混用。

檔案雜湊比對保留完整 sha256。丟回應的案例要保存 commit 前後的時序與原回執。真機操作案例要保存前後的領域狀態、原 operation ID、停止的時點，以及無法確認的時間窗。

效能與成本驗收另附同一場景的前後測量，用相同的裝置、網路、後端與任務交錯跑。量測前不寫「更快」「更省電」或節費百分比。
